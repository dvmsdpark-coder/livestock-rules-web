# 문서 갱신 안내

이제 PDF 개정 때마다 기존 검색어 설정을 처음부터 다시 만들 필요는 없습니다. 기존 검색 엔진과 표현 사전을 유지하고, 개정으로 달라진 원문·연결·검색 결과를 따로 검토합니다. 다만 번호·본문 구조·SOP 절 구성이 바뀐 경우에는 자동 검사만으로 법률상 의미를 확정할 수 없습니다.

## 시작

1. Windows에서 저장소의 **Start-UpdateManager.cmd**를 실행합니다.
2. **http://127.0.0.1:4175/** 를 엽니다.
3. 갱신할 문서를 선택하고 새 PDF, 버전, 시행일 또는 검색 기준일을 입력합니다. 공식 시행일이 미확인이라면 날짜 설명에 근거를 남깁니다.

Python 3.12 이상과 Node.js 22 이상이 필요합니다. 현재 PC의 Codex 런타임이 있으면 시작 스크립트가 자동으로 찾습니다. 다른 PC에서는 Python·Node.js를 설치하고 `python -m pip install -r maintenance/requirements.txt`를 한 번 실행합니다. Docker와 Linux는 이 도구의 실행에 필요하지 않습니다. 과거 관리 DB를 지우기 전에는 별도로 백업하세요.

이 관리 서버는 PC의 127.0.0.1에만 연결합니다. GitHub Pages 이용자는 이 화면에 접근하지 않습니다. PC가 꺼져도 기존 공개 검색 사이트는 계속 동작합니다.

## 갱신 순서

### 1. 후보본 만들기

기존 공개본을 덮어쓰지 않고 `private/updates/<후보번호>/`에 새 PDF·추출 색인·검토 설정을 만듭니다. PDF 문서명, 날짜, 파일 크기와 원문 해시를 확인합니다. 기존 11개 문서 종류의 누락을 검사합니다.

새 PDF의 본문과 조문, 별표·별지 후보를 추출합니다. 이전 페이지 범위는 새 PDF에 자동 재사용하지 않습니다. 동일 파일·같은 버전·같은 기준일이면 기존 승인 색인을 사용하는 **재현 검사**가 되며 공개본은 바뀌지 않습니다.

### 2. 달라진 원문 검토

변경·추가된 새 페이지와 삭제된 기존 페이지를 확인합니다. 줄바꿈 차이만으로 불필요하게 비교되지 않도록 공백을 정규화해 페이지를 대응시키지만, 실제 발췌 내용은 원문 그대로 보관합니다.

- 본문, 표, 서식, 그림, 공백, 간지를 구분합니다. 표·그림의 OCR 문자를 문장형 답변으로 간주하지 않습니다.
- 별표·별지의 **실제** 시작·끝 페이지를 확인합니다. 본문의 첨부 목록과 별표 실체를 구분해야 합니다.
- SOP는 목차·과거 고시·참고자료의 제외 범위를 확인합니다.
- SOP 신고·이동제한 해제·소독 절차는 새 PDF에서 시작·끝 쪽과 실제 시작 제목을 지정합니다. 일반 본문 절 검색과 별개로, 이 세 절차의 기존 검증을 유지하기 위한 설정입니다.

현재 도구는 OCR 엔진을 포함하지 않습니다. 이미지뿐인 본문은 외부에서 원문 대조가 가능한 OCR 색인을 준비하거나 수동 검토 절차를 보완해야 합니다. 본문을 그림으로 분류하면 PDF 확인은 가능하지만 그 내용을 문장 검색으로 찾는다고 보장하지 않습니다.

### 3. 변경본 검사

검사는 후보 폴더를 대상으로 실행합니다. 실제 공개 자료는 아직 바뀌지 않습니다.

- PDF·색인 SHA-256, 전체 페이지, 발췌가 추출 원문에 포함되는지 확인
- 새·구 버전의 적용 기간 중복과 기존 문서 누락 확인
- 기존 자연어 질문·SOP 질문·조문 번호와 제목 도달성 재시험
- 인용 조문·항·호와 별표 연결 검증
- 최초 신고 경감, 최저 보상금, 계열화사업자 의무, 방역사 자격 등 사용자 제보 질문 재시험
- 변경·삭제·추가 조문과 **번호 변경 후보** 표시
- 동일 질문의 변경 전·후 근거·발췌 비교

실패가 있으면 반영할 수 없습니다. 조문이 이동한 경우 번호 후보를 보여주지만 자동으로 같은 의미라고 확정하지 않습니다. 연결 규칙이나 기대 근거를 원문에 맞게 수정한 다음 다시 검사해야 할 수 있습니다. 질문마다 처음부터 재설정하는 대신 실패·변경 목록을 묶어서 검토합니다.

### 4. 검토 완료 후 반영

변경·삭제 페이지와 결과가 달라진 질문을 확인하고, 날짜·범위·적용 조건의 검토 확인란을 체크합니다. **검토한 후보본 반영**을 누르면 이 PC의 `site/` 폴더에 새 버전을 추가합니다.

이전 PDF·색인은 남기고 이전 버전의 종료일을 새 버전 시작일로 설정합니다. 새 목록은 마지막에 교체하므로 새 PDF·색인이 준비되기 전에 공개 목록이 먼저 바뀌지 않습니다. 검사 후 PDF·색인·검토 설정·검색 코드·시험 기준이 바뀌거나 공개 자료가 다른 작업으로 변경되면 재검사를 요구합니다.

반영 기록은 `maintenance/releases/`, 새 PDF에 묶인 검토 설정은 `maintenance/profiles/`에 저장합니다. 개인 경로·검토 메모·업로드 파일은 `private/`에만 남습니다.

### 5. GitHub 공개

로컬 반영은 인터넷 게시와 별개입니다. 다음을 하나의 변경으로 GitHub에 올립니다.

- `site/data/manifest.json`과 새 PDF·색인
- `maintenance/profiles/`의 새 검토 설정
- `maintenance/releases/`의 반영 기록
- 번호·구조 변경 때문에 수정했다면 검색 코드와 시험 기준

개인 폴더나 DB 백업을 올리지 마세요. GitHub Actions가 기존 검색 검사, 갱신 절차 검사, 버전 적용 시작일별 검사를 통과한 경우에만 배포합니다. 새 파일을 올렸다고 검사 실패를 무시하고 게시하지 않습니다.

## 복원

같은 관리 화면의 **이번 반영 이전으로 복원**으로 이전 공개 목록을 복원할 수 있습니다. 이후 다른 갱신이 이미 반영되었다면 이를 덮어쓰지 않도록 복원을 차단합니다. 새 PDF 파일은 이력 보존을 위해 남겨둡니다.

인터넷에 이미 게시한 변경은 GitHub의 해당 커밋을 되돌리고 배포 검사를 다시 통과시켜야 합니다. 로컬 복원 버튼만으로 GitHub를 되돌리지는 않습니다. 반영 이력 파일도 해당 GitHub 변경과 함께 되돌립니다.

## 자동화의 범위

파일 추출·비교·재시험·검토 누락 차단·적용 기간 관리·복원을 자동화했습니다. 새 법령의 법률 해석, 표·그림의 의미, 모든 자연어 표현의 정확성까지 자동 승인하는 기능은 아닙니다. 개정으로 중요 조건이 바뀐 부분과 번호·구조 변경은 관리자가 확인해야 합니다.

## 명령줄

```text
python tools/update_manager.py
python tools/update_manager.py --prepare "새파일.pdf" --family <문서종류키> --version "개정번호" --from YYYY-MM-DD
python tools/update_manager.py --validate <후보번호>
python tools/update_manager.py --rollback <반영된후보번호>
python tests/update_workflow_test.py
npm run audit:release
```

명령줄에서도 검토 기록 없이 반영할 수 없습니다. 평상시에는 관리 화면을 사용합니다.
